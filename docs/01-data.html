Chapter 1

The data: what a model actually learns from

Finetuning doesn't feed a model textbooks — it feeds it thousands of tiny demonstrations: "when asked this, answer like that." This chapter shows one real demonstration from the project, the format it lives in, and how 1,000 raw Q&A pairs became the three files training reads.

One real training example

The project uses the Alpaca format: every example is a JSON object with three fields. Here is a sample from data/processed/medical_train.json, color-coded — the same colors are used throughout this chapter:

instruction — what the user asks
Recovery Outcome Measures: Is There a Place for Culture, Attitudes, and Faith?
input — optional extra context
[PURPOSE] Utilization of the Recovery Knowledge Inventory (RKI) and Recovery Attitudes Questionnaire (RAQ) in southeastern Australia raised questions about the RAQ, including links between attitudes, faith, and culture in supporting the recovery journey. (abridged)
output — the answer the model should learn to give
yes — This paper discusses the cultural appropriateness of the RAQ in Australian settings, and identifies the need to develop rigorous, inclusive recovery outcome measures. [Based on published research. Consult healthcare provider.]
Notice the disclaimer inside the output. The prep script appends "Consult healthcare provider" to every answer. Whatever pattern appears in every training output, the model will learn to reproduce — that is the whole mechanism of finetuning, used here deliberately as a safety habit.

What the model really sees

Before training, each example is pushed through a chat template (this project uses the Mistral template) and tokenized. The three fields collapse into one long token sequence:

<s>[INST] Recovery Outcome Measures: Is There a Place for … [PURPOSE] Utilization of the Recovery Knowledge … [/INST] yes — This paper discusses the cultural appropriateness … Consult healthcare provider.] </s>

The crucial trick — loss masking: the model reads the whole sequence, but the training loss is computed only on the green tokens (the output). The instruction and context are visible but never scored, so the model is not trained to parrot questions — only to produce answers. Gray tokens like [INST] are the template's scaffolding that tells the model where the user's turn ends and its own begins.

From 1,000 raw pairs to three files

scripts/prepare_medical_data.py does four things to the raw PubMedQA download — each is a pattern you'd see in any finetuning project, whatever the domain:

  1. Clean — regexes scrub patterns that look like phone numbers or SSNs (a privacy habit from the medical domain), and whitespace is normalized.
  2. Format — each record is reshaped into the three Alpaca fields shown above.
  3. Augment — the safety disclaimer is appended to every output.
  4. Shuffle & split — the pool is randomly divided 80 / 10 / 10:

Why three files? Train is what the model learns from. Validation (sometimes called the eval set) is held out so you can watch, during training, whether the model is improving on data it has not memorized. Test stays untouched until the very end — a final exam that cannot be gamed, because no decision was ever made by looking at it.

Gotcha from the real run: the training config never actually read medical_val.json. It pointed only at the train file with val_size: 0.1, which told LLaMA-Factory to carve the validation set out of the 800 train samples internally — so the run really trained on 720 samples and evaluated on 80, while the two prepared 100-sample files sat unused. Harmless here, but a good reminder: the config, not the folder, decides what the model sees. Chapter 3 picks this up again.

How the model reads text: tokens

Models never see letters — the tokenizer chops text into subword tokens, each mapped to an integer ID. BioMistral's vocabulary has 32,000 of them. A word like "pharmacokinetics" may be split into several pieces, while common words are single tokens. Two practical consequences for finetuning:

  • cutoff_len: 4096 in the config is measured in tokens, not characters — longer examples get truncated.
  • Cost and speed scale with token count, which is why this run's ~10-minute wall clock depends as much on answer length as on sample count.
