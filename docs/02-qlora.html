Chapter 2

QLoRA: how a laptop-class GPU trains a 7B model

Updating all 7.24 billion weights of this model the classic way needs server-class hardware — roughly 16 bytes of GPU memory per weight once gradients and optimizer state are counted, on the order of a hundred gigabytes. This run did it in ~16–18 GB. The trick is two ideas stacked: LoRA (train tiny side-matrices, freeze everything else) and quantization (store the frozen part in 4 bits). Together: QLoRA.

Idea 1 — LoRA: don't edit the weights, add a correction

Every layer of a transformer is built around big weight matrices. LoRA leaves each original matrix W untouched and learns a small correction beside it: two thin matrices A and B whose product has the same shape as W but far fewer parameters. A narrow middle dimension r (the rank) keeps A and B small; a scale factor α (alpha) controls how strong the correction is. The layer's output becomes Wx + (α/r)·BAx — original behavior plus a learned nudge. In this config, r = 32 and α = 64, so α/r = 2.

The thinness is the point: r is the width of the bottleneck between A and B. For a 4096×4096 matrix, full finetuning would update 16.8M numbers; the A/B pair at r=32 has just 0.26M — 64× fewer. This config applies such a pair to every linear layer (lora_target: all), which across 32 transformer blocks adds up to:

Idea 2 — quantization: shrink what you froze

Frozen weights receive no gradients, so they only need to be read, not updated — and a read-only copy can be compressed. QLoRA stores each frozen weight in 4 bits using the NF4 code (NormalFloat4: 16 quantization levels spaced to match the bell-curve distribution real weights follow, so little information is lost). At compute time each block is briefly decompressed back to bf16 (bfloat16 — a 16-bit floating-point format used for the actual math), used, and discarded.

Why this combination works: quantizing weights you train breaks gradient descent — but LoRA already decided not to train them. The 4-bit base provides the knowledge; the bf16 adapters absorb the new behavior. Each idea makes the other affordable.

The exact recipe, from the config file

Everything above is controlled by a few lines of configs/biomistral_qlora.yaml:

### Method
finetuning_type: lora        # freeze W, train A/B pairs
lora_target: all             # attach a pair to every linear layer
lora_rank: 32                # r — bottleneck width (capacity knob)
lora_alpha: 64               # α — correction is scaled by α/r = 2
lora_dropout: 0.05           # light regularization on the adapter

### Quantization (the "Q" in QLoRA)
quantization_bit: 4          # store frozen W in 4 bits…
quantization_type: nf4       # …using the NF4 code

### Memory helpers
bf16: true                   # 16-bit math for everything computed
gradient_checkpointing: true # recompute activations instead of storing them

Two of these numbers become the villains of Chapter 4: lora_rank: 32 gives the adapter ~84M parameters of capacity — plenty to memorize 720 training samples rather than learn from them — and nothing here limits how long training runs. Hold that thought.
