Chapter 5

Using the result: a 321 MB personality for a 14 GB brain

Ten minutes of training did not produce a new model. It produced a small file — adapter_model.safetensors — that changes how the unchanged base model behaves. This chapter shows what that file is, how it snaps onto the base at chat time, and what a learner should do with this project next.

What training actually wrote to disk

Everything the run produced lives in outputs/biomistral-medical/: the trained A/B matrices from Chapter 2 (adapter_model.safetensors), a recipe card saying where they attach (adapter_config.json), the logs Chapters 3–4 were built from, and two full checkpoints. This asymmetry is LoRA's deployment superpower: one copy of the heavy base model can serve many adapters — a medical one, a legal one, a customer-support one — each a few hundred megabytes, swappable at load time, cheap to store and share.

How chat wires them together

configs/chat.yaml is the whole wiring diagram — four decisions, each echoing a chapter of this walkthrough:

model_name_or_path: models/biomistral-7b          # the frozen base (Ch. 2)
adapter_name_or_path: outputs/biomistral-medical  # + the trained adapter (Ch. 2)
template: mistral                                 # same template as training (Ch. 1)
quantization_bit: 4                               # same 4-bit loading as training (Ch. 2)
The template must match. The model learned to answer inside [INST] … [/INST] scaffolding (Chapter 1). Serve it with a different template and quality quietly degrades — one of the most common silent bugs when deploying finetuned models.

To talk to it:

./scripts/chat.sh

What finetuning changed is the behavior, by construction from the training data: answers that lead with a yes/no verdict, then reasoning in PubMedQA's register, then the safety disclaimer the prep script stamped on every training output. The base knowledge was already there — BioMistral was pretrained on medical literature; the adapter taught it a format.

What to do with this project next

The best exercises this repo supports, in order:

  1. Run the fixed config. Apply Chapter 4's fix table to configs/biomistral_qlora.yaml, retrain (~10 minutes), and overlay the new eval curve on the old one. Watching the gap shrink is the most instructive ten minutes in finetuning.
  2. Grade both models on the untouched exam. medical_test.json — 100 samples no run has ever seen (Chapter 1's gotcha means even the val file is pristine). Compare base vs. run-1 vs. run-2 answers side by side.
  3. Compare the two checkpoints. Point adapter_name_or_path at checkpoint-100 instead of the final adapter — per Chapter 4, the earlier checkpoint should generalize slightly better. Checkpoints aren't just crash insurance; they're time travel.
  4. Swap the domain. Nothing in this pipeline is medical except the data and the base model. New Alpaca-format JSON + any base model + the same configs = a finetune for your own domain.

⚠️ The finetuned model is an educational artifact. It answers medical questions in a convincing register — and Chapter 4 showed exactly how much to trust convincing: never use it for real medical decisions. That lesson, too, generalizes.
